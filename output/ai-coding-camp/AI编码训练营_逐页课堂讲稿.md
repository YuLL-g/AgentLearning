# AI 编码训练营｜逐页课堂讲稿

对应课件：[index.html](index.html)，共 24 页。下面的正文可直接按口语讲述；*【操作】* 是放映、提问或现场演示提示，不必念出。涉及练习项目的构建、测试和提交，均指独立的 `myls` 练习仓库，不是在本课程资料仓库操作。

## 第 1 页｜AI 编码训练营

大家好，欢迎来到 AI 编码训练营。今天我们按“先理解，再动手”的顺序走。前半部分先弄明白：编码 Agent 到底怎么工作？它为什么能够读文件、运行命令、帮我们修改代码？它又为什么有时会理解错需求，或者做出我们没要求的事？

后半部分，我们会用一个小项目练手：从零实现精简版 `ls` 命令，程序名叫 `myls`。重点不只是把代码写出来，而是把需求澄清、项目约定和测试驱动开发串成一个能反复使用的工作方法。先从 Agent 的发展脉络看起。

## 第 2 页｜AI 编码 Agent 的发展脉络

这张时间线不用背年份，我们看能力是怎样逐渐组合起来的。早期的重点是让模型理解和生成文本；模型规模和能力提升后，人可以用对话的方式提出任务、补充信息。检索和工具调用进一步让模型有机会获取外部资料、请求执行动作。再到今天，这些能力被组织进 Cursor、Claude Code、Codex 等编码产品里。

图上几个时间段是重叠的，不是一个阶段结束，下一个才开始。下面的“模型 + 工具 ≈ Agent”也只是课堂上的简化比喻：模型负责判断，工具提供行动的可能。真正跑起来，还需要有一套机制组织上下文、执行工具、处理结果并控制何时结束。我们下一页就把这套机制拆开看。

## 第 3 页｜最小 Agent 的运行时序

这张图有五个角色：用户、Agent、会话上下文、语言模型和工具。举个例子，我们说“帮我看看项目里有哪些文件”。Agent 会先整理这轮问题和相关历史，再把当前可见的信息、可用工具一起交给模型。

模型可能判断：“我得先列一下目录。”这里要注意，**模型提出工具调用请求，Agent 才负责实际执行**。工具返回文件列表，或者返回一个错误，Agent 都会记录下来，再把更新后的信息交给模型判断。需要更多信息，就继续调用工具；不需要了，模型给出最终答复，Agent 再回复用户并保存本轮记录。

所以，一次任务可能是“思考、调用工具、看结果、再思考”的循环，也可能一步就直接回答。下一页换一张流程图，看看 Agent 在这个循环里还要把住哪些关口。

## 第 4 页｜AI Agent 的最小运行框架

从左往右看，Agent 先组装本轮请求。用户刚说的话、必要的会话历史、项目规则和工具说明，都可能成为模型这次能看到的信息。模型据此决定下一步：直接答复，或者请求某个工具。

如果模型要调用工具，Agent 还得检查参数是否合理、有没有权限、是否超过运行上限，然后才能执行。执行完成后，再把输出、错误或状态交回模型。这一步可以重复很多次，也可能一次都不发生。

有两个边界请大家记住：模型并不是自己在终端里敲命令；而如果工具被拒绝、超时或达到上限，也应如实说明，不能把“停止了”说成“完成了”。这张图是通用工作方式的教学示意，不代表某个产品的全部内部细节。既然框架是相通的，具体用哪个编码 Agent，就值得按任务来选。

## 第 5 页｜Claude Code 不是唯一选择

课程后面会用 Claude Code 做演示，但它只是可选工具之一。图上的每个点，是一组模型、Agent 和推理设置在 Databricks 自有代码任务上的评测结果；横向看成本，纵向看通过率。它能提醒我们：换一个组合，成本和表现都可能变化。

不过，别把这张图当成所有项目通用的产品排行榜。评测任务、模型、设置不同，结果就可能不同；某个点更高，也不能简单说都是 Agent 品牌带来的差别。更实用的选择方法，是拿自己项目里的**同一个真实任务**试跑几种组合，比较完成质量、耗时、成本和操作体验。找到适合自己工作流的，比追一个统一的“第一名”有用。接下来，我们看看无论用哪个 Agent，都绕不开的上下文问题。

## 第 6 页｜Agent 会话中的消息持续累积

*【操作】让动画播放几秒，等消息增长到十几条时稍作停顿。*

请看画面：从规则和用户问题开始，接着可能有模型发出的工具请求、工具返回的结果、模型给出的答复。下一轮提问来了，就继续往后追加。图中已经不止七条消息了，中间和末尾的省略号表示还有更多记录，并不是说一段会话只能保存画面上这些内容。

连工具请求和工具结果也各自占一条记录，所以做几步操作后，会话很容易变长。但这里要分清两件事：**会话保存了多少消息**，和**某一次模型调用实际看见多少内容**，不一定相同。具体产品可能截取、摘要或按需组织历史。那当本轮可见的信息也变得很长时，会有什么影响？下一页看一条示意曲线。

## 第 7 页｜上下文变长，模型表现可能下降

先看横轴，它表示**单次模型调用实际可见的上下文长度**，不是刚才那页会话保存的消息总数。纵轴是相对任务表现。曲线前段比较平稳，中间慢慢下滑，接近窗口上限时下降更快，用来表达长上下文可能带来的问题。

这是一张概念图，**不是某个模型测出来的成绩曲线**。真实表现会随模型、任务、信息放在哪里，以及输入内容本身而变化；窗口上限也不是所有模型共有的一道性能断崖。我们要记住的是：能装下很多 Token，不等于每次都该装满。信息太多、太杂，重要线索就更难被聚焦。那怎样把真正有用的内容交给 Agent？下一页接着说。

## 第 8 页｜消息会累积，当前上下文要精选

左边是不断增长的会话记录，右边是这一轮真正需要用到的线索。我们可以先问四个问题：这轮到底要做什么，怎样才算完成？项目有哪些长期有效的规则？权威资料在哪个文件、哪个章节？前面已经验证了什么，还有什么没解决？

比如，只对 Agent 说“继续修”，它很难知道我们现在最在意什么。换成“修这个失败用例；失败命令是……；实际输出是……；期望输出是……”，下一步就清楚多了。长期约定可以放在精简的项目指令中，本轮特有要求放在本轮任务里。具体如何截取或摘要历史，要看 Agent 的实现。我们再把这些想法整理成四个可操作的步骤。

## 第 9 页｜四步把上下文变成可执行线索

这四步可以按“目标、资料、轮次、反馈”来记。第一步，**定目标**：这次只完成什么、边界在哪里、什么结果算通过。第二步，**给线索**：指出可信的文件和章节，让 Agent 找到依据，而不是让它在一大堆材料里猜。第三步，**控轮次**：大任务拆成一个个能验收的小任务，交接时说明已完成、已验证和待解决的内容。

第四步尤其重要，**用证据反馈**。如果测试失败，不只说“还是不对”，而是给出运行命令、实际输出、期望结果和相关约束；修完以后，再跑受影响的验证。这样，Agent 下一轮看到的是事实，不是一句模糊评价。当然，文字写得再好，也不能代替真实可用的工具、权限和运行环境。说到长期规则，下一页看看项目指令文件是怎样进入上下文的。

## 第 10 页｜CLAUDE.md 启动时自动进入上下文

*【操作】让左侧终端输入 `claude`，观察右侧上下文窗口的变化。*

现在假设我们已经进入一个练习项目，里面有适用的 `CLAUDE.md`。在终端启动 Claude Code 后，它会在会话开始时读取这类项目指令。也就是说，我们还没输入具体任务，模型当前可见的信息里就已经有一份项目约定了，比如先看相关文件、只改本轮范围、修改后做验证。

可以把它理解成新同事入项目前先拿到的“项目须知”，省去每次重新解释的功夫。图上的“01”表示本页强调的是**启动阶段的项目指令**，不是说它在所有系统信息里绝对排第一；右侧窗口也只是教学示意，不是真实界面截图。实际会话里可以用 `/context` 查看加载情况。既然它会反复影响后续任务，我们就得想清楚：文件里到底该写什么？

## 第 11 页｜CLAUDE.md / AGENTS.md：写什么？

项目指令文件不用写成一本手册。真正值得放进去的，是**长期适用、项目特有、具体可检查**的内容。可以归成四类：项目是做什么的、以哪份规格为准；源码和测试在哪些目录、真实的构建和测试命令是什么；哪些兼容性、错误处理和修改边界不能越过；以及修改后怎样验证、交付时要报告什么。

比如“保证代码质量”就很空；“改完运行项目测试，并报告失败项”更容易执行。临时任务放在当前提问里，完整规格放在专门文档里，项目指令只需指向正确的位置。`CLAUDE.md` 和 `AGENTS.md` 选哪个，也要看实际使用的工具与配置；有文件不等于 Agent 一定正确加载，更不等于规则成了强制权限。理解了项目上下文怎样准备，我们就进入动手实践。

## 第 12 页｜从零实现精简版ls命令

从这一页开始，我们从“Agent 怎样工作”切换到“怎样和 Agent 一起开发”。练习题目是从零实现精简版 `ls`，我们的程序叫 `myls`。右边终端里的文件名和输出，只是目标效果的示意，不是现在已经运行出来的成果。

这次实践有四条方法：**先澄清需求；按需求做最小实现；逐步增量开发、每步验证；测试先行，先写测试再实现。**这里的“精简版”不等于复制系统 `ls` 的所有行为。我们先别急着写代码。如果需求提出人只留下一句“从零实现精简版 ls 命令”，你会先问什么？

## 第 13 页｜先把一句话需求问清楚

左边这一句话听起来像个完整题目，但真正动手时，问题会接连冒出来：用什么语言？在哪个平台运行？“精简”到底包含哪些功能？怎么判断做完了？如果这些问题没人回答，不同开发者做出的程序可能都“看起来像 ls”，但彼此完全不一样。

所以，我们先和需求提出人沟通，形成右边更具体的交付目标：用 C 语言，在 Linux 上开发 `myls`；说清支持的选项、路径参数数量，以及多列、颜色、递归等不做的范围。比如 `-h` 必须和 `-l` 一起使用，不能让 Agent 自己猜。输出字段、排序、时间和错误行为，再交给后面的验收契约确定。

请留意最后一句：系统 `ls` 只是部分语义的参考，不是逐字节照抄的标准答案。需求澄清做的事，就是把“我以为”变成双方能够共同检查的约定。目标具体多了，如果现在一股脑交给 Agent 一次生成，会怎样？

## 第 14 页｜把交付目标直接交给 Agent

*【操作】先不点按钮，请学员猜一猜；听过几种猜测后，点击“揭示可能的问题”。*

我们做个思想实验：把刚才的交付目标原样发给 Agent，没有补充版本控制、项目结构、开发节奏和验证方式，直接说“请一次完成”。它可能很快产出代码。可我们拿到代码后，应该检查什么？

这页列出的不是必然发生的结果，而是现场演示时值得观察的风险：有没有版本历史？源码、测试和文档是否放在合适的位置？构建产物是不是混进了交付目录？如果全部功能一次写完，出错时好不好定位、好不好审核？还有一个关键点：如果先写实现、后补测试，测试会不会只是在迁就已经写好的代码？

真正的结果要以独立练习仓库里的现场演示为准。为了让开发可控，我们先得把“到底要实现哪些行为”整理成清单。

## 第 15 页｜需求列表

经过需求分析和评审，我们拿到了这张需求列表。左边是**遇到的场景**，右边是**约定的行为**。例如，不给路径就列当前目录；给一个目录就列那个目录；给多个路径明确报错。普通模式每行输出一个名称，不显示隐藏项，并按字节序升序排列。

选项也是逐个定义的：`-a` 包含以点开头的条目，包括 `.` 和 `..`；`-t` 改成按修改时间排序；`-l` 输出课程规定的固定长格式；`-h` 只改变长格式里的大小字段，单独使用要报参数错误。`--help` 应直接输出帮助并成功退出，不去读取目录。路径不存在或无权限时，错误写到标准错误，不能在标准输出里伪造结果。

这张表解决的是“要覆盖哪些行为”。要做成可验收的程序，还得进一步说清字段、排序细节、时间格式和错误退出码。下一页就是更细的验收契约。

## 第 16 页｜验收契约

如果上一页回答“要做哪些事”，这一页回答“怎样才算做对”。规则不少，不必逐字朗读，我们抓几处最影响实现和测试的地方。

先看参数：短选项可以合写或分写，选项要在路径前；路径必须是目录；`--help` 只能单独使用。再看排序：默认按名称升序；用了 `-t`，按修改时间从新到旧，时间相同还要按名称升序，这样结果才确定。读目录条目元数据时用 `lstat`，所以符号链接按链接本身处理。长格式的字段顺序、空格、UTC 时间，以及 `-h` 的大小换算，都有课程自己的固定规则，不能直接复制某台机器上的系统 `ls` 输出。

下面的小例子最适合拿来写测试。`demo` 里有 `a`、`b` 和 `.hidden`：普通模式只输出 `a`、`b`；加 `-a` 后，还要包含 `.`、`..` 和隐藏项。单独用 `-h`，或者访问不存在的路径，应返回错误。如果读目录或取某个条目的元数据失败，整次操作都应失败，不能先打印一半结果。验收时要分别看**标准输出、标准错误和退出码**，不能只看屏幕上有没有几行字。有了这份契约，我们才适合搭工程骨架，按小步开发。

## 第 17 页｜从需求契约进入开发

现在才真正进入开发阶段。先在**独立的 `myls` 练习仓库**初始化 Git，再建工程骨架：`.gitignore`、`Makefile`、`include/`、`src/`、`tests/` 等各有位置。接着写 `CLAUDE.md`，告诉 Agent 项目目标、权威需求、真实命令、开发边界和验证方式。然后做一次 `build project skeleton` 的初次提交，留下可回退的工程起点。右侧目录树展示的是计划建立的结构，不是本课程资料仓库里的源码。

之后按小步开发。图里的常见 TDD 循环是 **Red、Green、Refactor**：先写当前行为的测试并确认它失败，再写最少代码让它通过，最后整理代码并保持测试通过。本课程的实践还强调 **Review**：人要审查测试断言、实现范围和回归结果，确认后再提交。不要在 Red 阶段就把未通过的测试提交成基线。项目骨架有了，下一页具体看 `CLAUDE.md` 怎么写。

## 第 18 页｜CLAUDE.md 怎么写

*【操作】先问“如果现在让你写，第一稿从哪里来？”，再点击“查看两种写法”。*

第一种是直接创建 Markdown 文件，自己写。适合已经熟悉项目事实，也清楚哪些约定需要长期保留的人。第二种是在 Claude Code 会话里先运行 `/init`，让它生成初稿；然后提供交付目标和协作要求，人工增删改，再请它继续优化。这里的 `/init` 和后续提示词是**连续两步**，不是一条固定的“`/init + 提示词`”命令。

*【操作】打开“查看示例提示词”，展示可复制内容；返回后再打开“其他信息”。*

示例里包含交付目标、开发原则和构建测试入口；“其他信息”还补上 TDD 的 Red → Green → Review 约定、提交纪律、测试视角与禁止事项。课堂上不必把长文本逐行念完，重点是提醒大家：AI 可以帮忙起草，**真实目录、命令、规则和验收依据仍要由人核对**。项目刚起步时，能供 `/init` 发现的信息也有限。写好共同的项目约定，下一页就用同一套起点比较三种开工路径。

## 第 19 页｜同一任务，三条开工路径

这次我们做一个对照：三次演示从相同的项目骨架、相同的 `CLAUDE.md` 出发，也使用同一句任务提示词：“开始需求开发，需求场景：无路径参数；行为：列出当前目录。”普通对话可能直接着手处理；Plan 模式先探索项目、提出计划供人审查；Grill Me 是第三方 Skill，先通过多轮提问挖出没有说清的选择。

*【首次到本页】先请学员记下观察点和自己的猜测：Agent 会先问什么？什么时候写代码？谁来确认假设？测试会覆盖什么？此时先不点击“期望输出”。可以说：“先别看答案，下一页我们写下演示前预测。”*

*【三条路径现场演示后返回本页】点击“期望输出”，再讲下面这段。*

按钮里藏着本次对照实验的讲师预设：包含隐藏项但不包含 `.`、`..`，不做排序；测试非空目录、空目录、含空格名称，以及两个不同目录。这些条件**没有放进三条路径共用的任务提示词**。请注意，这是一组用于观察需求澄清能力的实验预设，**不替代第 15、16 页的完整 `myls` 验收契约**；两者对隐藏项和排序的规定不同。讨论时要明确当前采用哪一套约定，不能把实验结果直接当成正式需求的验收结论。看过预设以后，回到下一页核对预测。

## 第 20 页｜三种路径的演示前预测

这张表是**演示前的预测**，不是已经测出来的排名。我们从四个方向看：需求有没有问清楚？测试覆盖了关键场景吗？有没有擅自扩展？花了多少时间、需要多少人工介入？

普通模式可能启动得快，但没写明的细节也可能被自行补全。Plan 模式先把实施步骤摆出来，便于我们审查范围和方案；不过计划很完整，不代表需求一定问清。Grill Me 前期问答较多，可能更早暴露隐含假设，但问清之后还需要有人落实实现与验证。测试覆盖最终要看实际断言，不能只看对话听起来是否周全。

可以用三句话记住各自的主要作用：Grill Me 帮我们追问**要什么**，Plan 模式讨论**怎么做**，TDD 用测试先行、小步回归和人工审查来检查**做得对不对**。它们有交集，也都不能替人确认真实需求。现在把预测记下来，等现场演示后，再根据对话、代码和测试结果修正这张表。

*【操作】暂停放映，在有权限的独立练习仓库中，按相同骨架和提示词演示三条路径，记录提问、改动、测试和耗时。演示结束后返回第 19 页，点击“期望输出”，说明它只是本次对照的预设；再回到本页核对预测。之后翻到第 21 页。*

## 第 21 页｜实际开发中用什么模式

刚才把预测和现场过程对照以后，回到最实际的问题：开发时到底选哪种方法？答案取决于项目。需求已经非常清楚、改动也很小时，流程可以简洁些；需求模糊、边界多、修改代价高时，先澄清和审查计划就更值得。这里说的“模式”是课堂上的宽泛说法：Grill Me 是第三方提问 Skill，Plan 是 Claude Code 的工作模式，TDD 是开发方法。它们不是同一类开关，也没有固定的优劣排名。

接下来我们把它们串起来试一次：从工程骨架出发，先用 Grill Me 追问“要什么”，再用 Plan 模式形成并审查“怎么做”，最后按 Red → Green → Review 小步实现和验证。需要时还可以用 `/code-review` 辅助检查当前改动，但发现的问题仍要由人判断、修复和复验。看过这条路线，后续需求就交给大家练习。

*【操作】本页讲完后暂停放映，切到独立练习仓库带做一个小任务。先确认所在目录、工具权限和当前分支；让学员审查澄清结论与计划，再展示失败测试、最小实现、回归结果和改动 diff。完成后翻到第 22 页。*

## 第 22 页｜实践任务：完成后续需求开发

前面的带做演示了怎样开工。后续练习以**需求列表和验收契约**为依据，逐项实现并验证。不要只看程序能不能运行，还要回到约定的输出、错误和退出码上检查。

页面上有练习项目的仓库链接。开始前，先从已有基线创建自己的分支，分支名按 `工号1_工号2` 这个格式；只在新分支提交，不要直接提交到 `develop` 或 `master`。提交前看一眼当前分支、改动内容和验证结果。我们前面讨论的代码和命令都应发生在这个独立练习项目里。布置完任务，最后用一页把今天的方法串起来。

## 第 23 页｜课程回顾：从理解 Agent 到可验证交付

今天的内容可以串成四步。第一，理解 Agent 怎样把模型、工具和上下文连成一个运行循环。第二，为项目准备清楚的协作上下文，用适用的 `CLAUDE.md` 或 `AGENTS.md` 告诉它长期规则和验证方法。第三，面对模糊需求，先分析、澄清“要什么”，形成可以检查的行为和验收条件，再讨论“怎么做”。第四，用测试先行、最小实现和每步审查，把任务推进到可验证的结果。

这四步连起来才有用：Agent 再能干，也不会自动知道我们没说出的期望；计划再漂亮，也不能代替真实测试；测试全绿，也要确认断言本身对不对。把要求讲明白，把工作拆小，把结果验清楚，是今天最希望大家带回实际项目的方法。最后，感谢大家今天一起参与。
