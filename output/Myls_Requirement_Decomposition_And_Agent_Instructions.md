# 从“开发一个 `myls`”到可验证任务与 Agent 指令

> 用途：讲解开发者如何使用 Agent 辅助需求分析、任务拆解和 TDD。以下从**只收到一句话、尚无已确认详细契约**的情境出发。课程中的 [Outline.md](../Outline.md) 已包含最终答案；它应在澄清后作为需求方确认的契约使用，不能假装是开发者从一句话自然推导出的结论。

## 1. 原始需求能确定什么

原话：“开发一个 `myls` 工具。”

此时只确定了交付物名称和开发意图。目标用户、平台、语言、命令行格式、功能范围、输出和错误行为都未明确。即使名称让人联想到系统 `ls`，也不能据此自行加入颜色、多列、递归或选项语义。

第一轮使用 Agent 的目标是**找信息缺口**，不是生成代码：

```text
目前只收到“开发一个 myls 工具”。先阅读练习仓库已有说明和代码，
不要修改文件。将发现的信息分为“有依据且已确定”“待需求方确认”
“我方建议”三类，指出依据文件。按优先级列出会影响用户可见行为的
澄清问题；每个问题可以附候选方案，但不要把建议写成已确定需求。
本轮只交付需求分析，不编写测试或实现。
```

若练习仓库已经包含 `Outline.md` 或其他经确认的需求文档，Agent 应直接阅读并以其为依据；那已不再是“只有一句话需求”的情境。当前仓库是讲师资料库，[AGENTS.md](../AGENTS.md) 会指向完整课程大纲，因此课堂若要演示从模糊需求开始，需要另备逐步揭示材料的学员环境。详见[课程材料拆分说明](Myls_Requirements_To_Learner_Materials.md)。

## 2. 开发者向需求方澄清什么

先询问会改变外部行为、阻碍第一轮实施的问题。问题应带上背景或候选方案，便于需求方作决定。

| 问题组 | 需要确认的例子 | 答复进入哪里 |
| --- | --- | --- |
| 目的与范围 | 谁使用？是系统 `ls` 的完整替代品，还是教学用精简工具？第一版必须有哪些能力？ | 产品目标与范围。 |
| 运行约束 | 运行在哪个平台？必须用 C 吗？可用哪些依赖、编译器和接口？ | 技术约束。 |
| 命令行接口 | 接受几个路径？无路径时使用哪里？需要哪些选项？选项能否组合？ | 参数契约。 |
| 输出行为 | 一项一行吗？隐藏项、顺序、时间、大小、符号链接如何处理？ | stdout 的验收契约。 |
| 失败行为 | 无效参数、路径不存在、目录无权限时如何输出和退出？ | stderr 与退出码契约。 |

每项答复保留来源和状态：**已提供／待确认／开发者建议／已确认**。例如“`-t` 时间相同时按名称升序”是合理建议，但只有需求方确认后才是要求。Agent 可帮助找遗漏、整理选项和起草记录；开发者负责核对，需求方或有权决定者确认用户可见行为。

## 3. 把答复变成可验证的行为契约

以下**假设**需求方确认了课程 [Outline.md 第四节](../Outline.md) 的规则。这些规则是示范用的已确认结果，不是原始一句话自带的信息。

| 条目 | 已确认行为的写法 | 可观察的验收角度 |
| --- | --- | --- |
| 无路径 | `myls` 读取当前目录。 | 在指定工作目录执行，检查输出、stderr 和退出码。 |
| 一个目录路径 | `myls DIR` 读取 `DIR`，不固定读取当前目录。 | 用内容不同的两个目录验证路径生效。 |
| 普通模式 | 隐藏项不显示；每项一行；按名称升序。 | 创建 `a`、`b`、`.hidden`，检查完整 stdout。 |
| 错误 | 路径不存在或参数不合法时，stdout 为空，stderr 输出说明，退出码为 1。 | 分别捕获三个通道，不只搜索错误文字。 |

对每个场景，都写清**给定参数与文件系统状态 → stdout、stderr、退出码**。类似“正常显示目录”或“错误处理合理”的文字不足以作为验收标准。复杂选项的细则，例如 `-h` 舍入、`-t` 同时间排序、符号链接行为，应在对应功能实现前确认；不能在提交后用未公布的规则判错。

## 4. 从完整契约拆成小任务

建议按依赖关系安排增量，任务列表可随澄清结果调整。本课程采用 [Outline.md 第五、六节](../Outline.md) 的路径：

1. 无路径时读取当前目录。
2. 一个有效目录参数使读取目标切换到指定目录。
3. `--help`、普通模式的隐藏项过滤和名称排序，以及基础错误处理。
4. 分别实现 `-a`、`-t`、`-l`、`-h`，再覆盖关键组合。

每轮任务卡至少包含：**目标、输入与场景、预期输出和退出码、当前不验收的事项、完成证据**。先列整体测试场景，再针对当前任务写少量测试；不必在开工前写完所有选项的测试。

### 示例任务卡：一个有效目录参数

前提：无参数读取当前目录的上一轮任务已经通过。

| 项目 | 本轮内容 |
| --- | --- |
| 目标 | `myls DIR` 读取传入的目录，而非当前目录。 |
| 输入场景 | 两个内容不同的有效目录；另考虑空目录和含空格的名称。 |
| 阶段验收 | 可见条目每项一行、恰好出现一次；退出码 0，stderr 为空。 |
| 本轮暂不验收 | 隐藏项是否输出、名称顺序、无权限、选项解析。 |
| 完成证据 | 新测试因缺少指定目录功能而失败；最小实现后新增测试和旧测试通过；审查 diff。 |

这张卡使用大纲 [5.1 的阶段验收](../Outline.md)。测试比较过滤后的可见名称集合，暂不要求排序或隐藏项过滤。后续“普通模式”必须补齐最终契约；阶段标准不能替换最终标准。

## 5. 把任务卡转换成 Agent 指令

一条可执行指令通常交代六件事：**权威依据、当前目标、可观察验收、改动范围、验证动作、交付报告**。不要把整个项目的所有功能塞进当前一轮，也不要要求 Agent 猜测尚未确认的语义。

### Red：只写当前行为的测试

```text
先阅读 Outline.md 中“5.1 无路径参数、一个目录参数”的阶段验收、
AGENTS.md 和现有测试。本轮只为“一个有效目录参数”增加测试。

仅修改 tests/，不要改生产代码。用内容不同的两个临时目录证明
传入路径生效；覆盖空目录及含空格名称的场景。分别检查 stdout、
stderr、退出码；按阶段契约比较可见名称是否各出现一次，暂不
断言名称顺序或隐藏项过滤。

运行 make test，确认新增测试因尚未支持指定目录而失败。报告
失败命令与原因，然后交给我审查断言。
```

开发者先检查测试是否忠实于已确认契约，以及红灯是否确实来自功能缺失。编译失败、夹具错误或断言越界都不算有效的 Red。

### Green：实现已审核测试对应的行为

```text
新增测试已审核。只实现使“一个有效目录参数”测试通过所需的
最小 C 代码，保持无参数行为可用。不要提前加入排序、隐藏项
过滤、其他选项或长格式，也不要放宽测试断言。

运行 make all 和 make test；检查 git diff、目录句柄释放及错误
路径。报告修改文件、测试命令与结果、尚未覆盖的行为。
```

### Review：核对结果与范围

开发者核对新增和旧测试、完整 `git diff`、资源生命周期及当前任务卡；如果发现缺陷，让 Agent 做局部修复并重新回归。全部通过后形成一个可独立回滚的提交，再进入下一轮。

## 6. 课堂上要让学员看到的转换关系

| 层次 | 这个例子的内容 | 谁负责决定或核对 |
| --- | --- | --- |
| 原始需求 | “开发一个 `myls`。” | 需求方提出。 |
| 待澄清问题 | 是否支持指定目录？如何输出和报错？ | 开发者提出，Agent 可辅助查漏。 |
| 已确认契约 | `myls DIR` 的路径和可观察行为。 | 需求方确认，开发者记录。 |
| 当前任务卡 | 只实现有效目录参数及本轮阶段验收。 | 开发者拆分并审查。 |
| Agent 指令 | 指定依据、目标、范围、测试和汇报方式。 | 开发者发出并持续核对执行结果。 |
| 验证证据 | 真实 Red、Green、回归和 diff。 | 测试与人工审查共同提供。 |

**课程要点**：清晰的 Agent 指令来自已确认的行为和可验收的小任务。高质量上下文不只是更多文字，还包括准确的权威文件、当前任务边界，以及执行后得到的测试证据。
