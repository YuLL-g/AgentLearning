# 一个实际代码仓库的 `AGENTS.md` 应写什么

> 适用场景：给编码 Agent 提供长期有效的仓库协作规则。以下以**虚构的 C 协议解析库 `libpacket`**为例，与本仓库的课程项目无关。示例路径和命令需要按实际项目替换。

## 核心定位

`AGENTS.md` 应让刚进入仓库的 Agent 尽快回答三个问题：**项目要做什么、哪些约束不能破坏、怎样验证改动正确**。它适合承载稳定、项目特有、可执行的约定；一次任务的需求和进度不应长期留在其中。OpenAI Docs 将项目目标、编码约定、测试标准、相关资料、特殊行为及范围边界列为常见内容。[开发工作流示例](https://developers.openai.com/cookbook/examples/codex/iterating-development-workflows-with-codex)

## 建议包含的七部分

| 部分 | 需要说明什么 | `libpacket` 示例 |
| --- | --- | --- |
| 1. 项目定位与权威来源 | 项目用途；行为、接口、架构发生歧义时以哪个文件为准。 | “本库解析二进制报文；协议语义以 `docs/protocol.md` 为准，公开接口以 `include/packet.h` 为准。” |
| 2. 仓库导航 | 主要模块、测试、文档的位置，以及按任务读取哪些资料。 | “解析代码在 `src/parser/`，夹具在 `tests/fixtures/`；修改报文格式时查看协议文档。” |
| 3. 环境与命令 | 支持的平台、语言版本、构建入口、相关验证命令。命令应在真实仓库中可运行。 | “C11；用 CMake 构建；用 CTest 运行测试。” |
| 4. 实现约束 | 项目独有且影响正确性的规则，包括兼容性、内存所有权、错误处理等。 | “公开 ABI 保持兼容；读取输入前检查剩余长度；每条错误路径释放已取得资源。” |
| 5. 测试与验收 | 哪类修改要运行哪些测试，关键边界场景是什么，怎样报告无法验证的部分。 | “修改解析逻辑时验证正常、截断和长度字段越界报文。” |
| 6. 修改边界与协作方式 | 哪些操作需要特别判断；遇到未定义行为或资料冲突时如何处理。 | “不自行发明协议字段；改变公开 API 前说明调用方影响。” |
| 7. 交付要求 | 完成任务时报告哪些证据。 | “列出改动、对应规格、执行命令及结果、未验证风险。” |

上述是内容框架，不意味着每个仓库都要写满七个标题。小仓库可以合并章节；复杂仓库可让根文件只写通用规则，再在特定子目录放置更具体的指引。[OpenAI Docs：分层项目指令](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

## 完整示例：虚构的 C 代码库

```md
# libpacket 仓库协作指引

## 项目与依据

- 本仓库提供 C11 二进制协议解析库 `libpacket`。
- 报文字段、合法性和错误行为以 `docs/protocol.md` 为准；公开接口以 `include/packet.h` 为准。
- 需求与上述文件冲突时，指出具体差异，不自行猜测协议行为。

## 代码位置

- `src/parser/`：解析实现；`include/`：公开头文件。
- `tests/unit/`：独立逻辑测试；`tests/fixtures/`：有效和畸形报文样本。
- 修改报文格式时读 `docs/protocol.md` 的相关章节；修改公开接口时检查调用方。

## 构建与验证

- 配置：`cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug`
- 构建：`cmake --build build`
- 测试：`ctest --test-dir build --output-on-failure`
- 修改解析逻辑时，验证正常报文、截断报文和长度字段越界。
- 修改公开头文件时，检查现有调用方是否仍可编译。

## 实现约束

- 使用 C11；不引入新的运行时依赖。
- 访问输入缓冲区前必须检查长度，不依赖输入以 NUL 结尾。
- 明确内存的分配与释放责任；错误路径也要释放已取得的资源。
- 未经任务明确要求，不改变公开函数签名或错误码含义。

## 修改与交付

- 先阅读任务涉及的规格、代码和测试，再确定改动范围。
- 不通过削弱断言掩盖测试失败；区分原有失败与本次改动造成的失败。
- 完成后说明修改文件、对应规格、验证命令及结果、尚未验证的情况。
```

这份示例的价值在于**具体且可检查**：例如“访问缓冲区前检查长度”比“注意代码质量”更能指导实现与审查。构建命令也应取自真实仓库，而不是为了让文档完整而编造。

## 哪些内容不宜放在 `AGENTS.md`

- **完整需求规格**：将其放在产品或协议文档中，在 `AGENTS.md` 指明权威文件和适用时机。
- **本轮临时任务**：例如“今天先实现某个选项”，应放在任务指令中；任务结束后不应继续约束其他工作。
- **详细架构说明和长教程**：保留在专门文档中，按任务指向相关章节，避免每次工作都加载无关内容。
- **工具已有的通用能力描述**：例如“读代码、认真思考、运行所有能想到的测试”，缺少仓库特性，也可能造成不必要的工作。
- **与实际环境不符的命令或过时规则**：会让 Agent 反复走错路径；发现后应及时修订。

OpenAI Docs 建议定期审视 `AGENTS.md` 中每一条规则是否仍有必要，并按任务指向相关文档，而不是要求每次修改都通读一组文档。[指令精简建议](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)

## 编写时的快速检查

1. **持久性**：下个月处理另一个任务时，这条规则是否仍适用？
2. **项目性**：它是否描述本仓库独有的事实或约定？
3. **可操作性**：Agent 能否据此决定读什么、改什么、运行什么、如何验收？
4. **准确性**：路径、命令、接口和权威文件是否与仓库现状一致？
5. **范围性**：规则是否仅适用于某个子模块？如果是，应放在更靠近该模块的位置。

最终目标不是写出尽可能长的文件，而是用少量准确、稳定的规则减少猜测，并让改动及其验证结果可审查。
