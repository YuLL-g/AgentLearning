# 不修改 Agent 内部代码，如何提高使用效果

## 核心结论

从广义上说，下面许多做法属于**上下文工程**：控制 Agent 在当前步骤能看到哪些目标、规则、资料和反馈。不过，使用者影响的并不只有模型输入，还包括工具是否可用、执行环境是否具备验证条件，以及何时由人审查和纠偏。这些选择不改变 Agent 的内部代码，却共同影响它能采取的行动和最终结果。

### 这些抓手与上下文工程的关系

| 抓手 | 与模型上下文的关系 | 还有什么作用 |
| --- | --- | --- |
| 明确任务、提供相关资料、维护项目规则、用证据反馈 | 直接改善当前或下一次模型调用可见的指令、事实与结果。 | 减少歧义和无依据的猜测。 |
| 控制每轮任务范围 | 改变每轮输入的目标和需要保留的历史，也属于上下文组织。 | 改变工作顺序，让每次改动更容易验收。 |
| 选择 Skill、MCP 和其他工具 | Skill 描述、加载后的说明、工具定义会影响模型看到什么以及如何选择工具。 | 启用或关闭工具还会改变**实际可执行的能力**；仅在提示词里描述工具，不能让不存在的工具变得可调用。 |
| 准备构建、测试和样例数据 | 工具运行产生的日志与测试结果会进入后续上下文。 | 可执行的环境让 Agent 获得真实反馈，作用不等同于预先写一段“测试应通过”。 |
| 人工审查与效果评估 | 将审查结论或失败证据反馈给 Agent 时，会成为下一轮上下文。 | 审查和评估本身是外部质量控制；即使尚未反馈给模型，也能发现不合格结果。 |

因此，“使用者主要通过控制输入上下文来提高表现”是一个**有条件成立的概括**：如果模型、工具、执行环境都完全固定，主要可控项确实是任务指令、项目资料、会话组织和反馈；如果还可以配置工具或准备测试环境，整体效果也会受这些实际能力与验证条件影响。这里的“输入”不只指用户当轮写的一段提示词，还包括 Agent 读取的文件、加载的说明、可见的工具定义和工具返回结果。具体内容何时被加载，取决于所用 Agent 的实现。

作为具体参照，[OpenAI Docs 的 Agents API 概览](https://developers.openai.com/api/docs/guides/agents-api/overview)分别描述 Agent 的指令与工具、执行环境和会话；[Codex 关于 Skill 与项目指令的文章](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)说明无关或冲突的说明会增加上下文负担。这支持上面的区分，但“上下文工程”本身没有必要被限定为某一种产品的正式分类。

## 可以直接采取的做法

| 抓手 | 具体做法 | 避免的常见问题 |
| --- | --- | --- |
| 明确任务和完成标准 | 写清目标、适用范围、不做什么、预期结果和验证命令。涉及行为契约时指出权威文件与章节。 | Agent 按自己的理解补功能，或把“代码写完”误认为“任务完成”。 |
| 提供相关而可信的上下文 | 指向需要读取的代码、需求、接口和失败日志；说明哪个文件优先。长材料给定位线索，让 Agent 按需读取。 | 关键信息缺失，或大量无关内容挤占注意力。 |
| 控制每轮任务范围 | 将可独立验收的大任务分成小轮；每轮明确交付物。跨轮继续时给出当前状态、已验证结果和未解决问题。 | 一次改动覆盖太多功能，难以审查和定位错误。 |
| 维护简短的项目规则 | 将长期有效的构建命令、目录约定、权威文件和验收方式写入 `AGENTS.md` 等项目指令；任务特有要求留在本轮请求中。 | 每次重复说明，或旧规则与新任务冲突。 |
| 只启用相关的 Skill 与工具 | 按任务选择 Skill、MCP 连接和工具权限；确认必需工具确实可用。若产品支持按需发现工具，可使用该机制。 | 无关说明或工具增加选择负担；过度精简又让 Agent 缺少完成任务的能力。 |
| 准备可执行的验证环境 | 确保依赖、构建入口、测试命令和样例数据可用；提供能复现问题的最小场景。 | Agent 只能推测正确性，无法通过运行结果发现缺陷。 |
| 用证据反馈，而非笼统重试 | 发现问题时指出失败命令、实际输出、期望输出和相关约束；要求修复后重跑受影响的验证。 | 反复说“再试一次”，却没有给 Agent 新信息。 |
| 审查最终结果 | 检查变更范围、测试结果、错误路径和未验证部分；必要时要求 Agent 给出文件与命令的具体依据。 | 表面上完成，实际遗漏边界条件或混入无关改动。 |

[OpenAI Docs 的提示设计指南](https://developers.openai.com/api/docs/guides/prompt-engineering)强调提供清晰指令和相关上下文；[Codex 关于 Skill 与 `AGENTS.md` 的建议](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)提醒避免积累冗长、互相冲突的说明。工具定义可按需加载，但是否支持及如何配置取决于具体产品；“只开相关工具”也不等于关闭完成任务必需的工具。[OpenAI Docs：Tool search](https://developers.openai.com/api/docs/guides/tools-tool-search)

## 能力边界

- 好的提示和项目资料不能补足模型完全不具备的能力，也不能代替缺失的必要工具或权限。
- Skill、MCP 和 `AGENTS.md` 的加载方式因产品而异；不要假设“已安装”就等于“本次模型已看到完整内容”。
- 如果执行策略、上下文裁剪或工具错误处理被产品固定，使用者只能通过任务组织、配置和反馈间接影响它们。持续出现同类失败时，应记录复现案例，交给 Agent 工具的维护者改进。
